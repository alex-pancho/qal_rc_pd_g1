## 1. Мислення атакуючого й `check --deploy`

Django з коробки робить для безпеки багато: автоматично екранує дані в шаблонах, вимагає CSRF-токен у формах, будує безпечні SQL-запити через ORM, зберігає паролі як хеші. Але захист ламається в двох місцях:

1. у **налаштуваннях** (наприклад, `DEBUG=True` у продакшені);
2. там, де розробник **свідомо обходить** захист (`|safe`, сирий SQL, `@csrf_exempt`, `fields = '__all__'`).

Існує список OWASP Top 10: це найпоширеніші категорії вразливостей веб-застосунків (актуальну редакцію дивіться на owasp.org). Ми розглянемо чотири: порушений контроль доступу, ін'єкції (SQL-ін'єкції, а в редакції 2021 року до цієї категорії віднесено й XSS), помилки в конфігурації та вразливі й застарілі компоненти.

У Django є автоматична перевірка налаштувань для продакшену:

```bash
python manage.py check --deploy
```

Команда виведе попередження: про `DEBUG`, секретний ключ, HTTPS, захищені cookie, HSTS. Кожне має код вигляду `security.WXXX`. Це наш чек-ліст на заняття. Запустіть її на початку й наприкінці та порівняйте, скільки попереджень зникло.

## 2. Налаштування: DEBUG, SECRET\_KEY, ALLOWED\_HOSTS

Три налаштування, які не можна залишати за замовчуванням:

- **`DEBUG`**: у режимі `True` помилка показує сторінку з кодом, налаштуваннями й значеннями змінних, а 404 перелічує всі маршрути. У продакшені має бути `False`.
- **`SECRET_KEY`**: Django підписує ним сесії, токени скидання пароля й інші дані. Якщо ключ витік, зловмисник може підробляти ці підписи. Тому ключ **не зберігають у git**.
- **`ALLOWED_HOSTS`**: список доменів, з якими сайт має право працювати. Захищає від підміни заголовка `Host` (на ньому, зокрема, будуються посилання в листах скидання пароля).

**Крок 1. Виносимо налаштування в змінні оточення** (`settings.py`):

```python
import os

SECRET_KEY = os.environ['DJANGO_SECRET_KEY']
DEBUG = os.environ.get('DJANGO_DEBUG', '0') == '1'
ALLOWED_HOSTS = os.environ.get(
    'DJANGO_ALLOWED_HOSTS', '127.0.0.1,localhost'
).split(',')
```

Зверніть увагу: за замовчуванням `DEBUG` вимкнений. Безпечний стан має бути станом за замовчуванням, а небезпечний вмикають свідомо.

**Крок 2. Генеруємо новий ключ:**

```bash
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

**Крок 3. Задаємо змінні перед запуском сервера:**

```bash
# Linux / macOS
export DJANGO_SECRET_KEY='ваш-ключ'
export DJANGO_DEBUG=1
```

```powershell
# Windows PowerShell
$env:DJANGO_SECRET_KEY = 'ваш-ключ'
$env:DJANGO_DEBUG = '1'
```

Якщо ви зберігаєте змінні у файлі `.env`, обов'язково додайте його в `.gitignore`. Django сам цей файл не читає, потрібна бібліотека на кшталт `python-dotenv` або `django-environ`.

Якщо старий ключ уже потрапив у git (наприклад, ключ із префіксом `django-insecure-` у початковому `settings.py`), вважайте його скомпрометованим і згенеруйте новий. Усі поточні сесії стануть недійсними, і це нормально.

**Що ви побачите на занятті:**

- З `DEBUG=1` відкрийте неіснуючу адресу `/abc/`: технічна сторінка 404 перелічує **усі** маршрути проєкту. Помилка в коді показує вихідний код і змінні. Для зловмисника це готова карта вашого застосунку.
- З `DEBUG=0` помилка показує лише `Server Error (500)`, а неіснуюча адреса просто `Not Found`.
- Запит із чужим `Host` отримує 400:

```bash
curl -i -H "Host: evil.com" http://127.0.0.1:5000/
```

При `DEBUG=0` команда `runserver` не віддає статичні файли, тому в адмінці зникне оформлення. Це не помилка: у продакшені статику віддає окремий сервер (nginx, WhiteNoise).

## 3. HTTPS і cookie

У продакшені сайт має працювати лише через HTTPS, а cookie мають передаватися лише захищеним каналом. У `settings.py`:

```python
USE_HTTPS = os.environ.get('DJANGO_HTTPS', '0') == '1'

if USE_HTTPS:
    SECURE_SSL_REDIRECT = True
    SESSION_COOKIE_SECURE = True
    CSRF_COOKIE_SECURE = True
    SECURE_HSTS_SECONDS = 3600
```

Блок вмикається лише змінною `DJANGO_HTTPS=1`. Інакше локальний `runserver` без HTTPS почне перенаправляти на `https://` і перестане працювати. Тому локально цю змінну **не вмикайте**; вона потрібна лише для перевірки `check --deploy`.

| Налаштування | Що робить |
| --- | --- |
| `SECURE_SSL_REDIRECT` | перенаправляє `http://` на `https://` |
| `SESSION_COOKIE_SECURE` | cookie сесії передається лише через HTTPS |
| `CSRF_COOKIE_SECURE` | те саме для cookie CSRF |
| `SECURE_HSTS_SECONDS` | браузер запам'ятовує, що сайт відкривається лише через HTTPS |

Будьте обережні з HSTS: браузер запам'ятовує це правило на вказаний час, і помилку важко виправити. Починайте з малого значення (година) і збільшуйте лише тоді, коли певні, що HTTPS працює стабільно.

За замовчуванням Django уже робить cookie сесії недоступною для JavaScript (`HttpOnly`) і додає `SameSite=Lax` для cookie сесії та CSRF. Це приклад безпечних налаштувань за замовчуванням.

Щоб побачити ефект, запустіть перевірку з усіма змінними (на Windows задайте їх окремо через `$env:...`):

```bash
DJANGO_SECRET_KEY='ваш-ключ' DJANGO_DEBUG=0 DJANGO_HTTPS=1 python manage.py check --deploy
```

Більшість попереджень має зникнути.

## 4. SQL-ін'єкції

SQL-ін'єкція виникає, коли дані користувача вставляють у текст SQL-запиту, і зловмисник може змінити сенс запиту. **ORM захищає від цього автоматично**: `BlogPost.objects.filter(title=user_input)` передає значення окремо від тексту запиту. Небезпека виникає, коли ви самі збираєте SQL із рядків: `raw()`, `extra()` або `cursor.execute()` з форматуванням.

Порівняйте в оболонці (`python manage.py shell`):

```python
from polls.models import BlogPost

title = "x' OR '1'='1"

# НЕБЕЗПЕЧНО: рядок вставлено в запит
unsafe = list(BlogPost.objects.raw(
    f"SELECT * FROM polls_blogpost WHERE title = '{title}'"
))
print(len(unsafe))   # поверне ВСІ пости

# БЕЗПЕЧНО: значення передано окремо
safe = list(BlogPost.objects.raw(
    "SELECT * FROM polls_blogpost WHERE title = %s", [title]
))
print(len(safe))     # 0
```

У небезпечному варіанті умова перетворюється на `WHERE title = 'x' OR '1'='1'`, яка істинна для кожного рядка. У безпечному весь рядок трактується як один звичайний текст.

**Правило:** ніколи не збирайте SQL через f-рядки й конкатенацію. Передавайте значення параметрами (`%s` і список).

**Ще одна пастка: довільні фільтри.** Не передавайте дані користувача у фільтр як ключі, наприклад `BlogPost.objects.filter(**request.GET.dict())`. Зловмисник сам вибирає, за яким полем (навіть за пов'язаними моделями) фільтрувати, і так може дізнатися приховані дані. Дозволяйте лише конкретні, заздалегідь відомі поля.

## 5. XSS

XSS (cross-site scripting) — це коли чужий скрипт виконується в браузері користувача *на нашому сайті*. Такий скрипт діє від імені користувача: може робити запити до нашого API з його сесією, читати сторінку, підміняти її вміст.

Django за замовчуванням **екранує** змінні в шаблонах: символ `<` стає `&lt;`, і браузер показує його як текст, а не як код. Небезпека з'являється, коли ми самі вимикаємо екранування.

**Приклад.** Додаємо сторінку, яка виводить пости (view, маршрут і шаблон):

```python
# polls/views.py
def post_list_page(request):
    return render(request, 'post_list.html', {'posts': BlogPost.objects.all()})
```

```python
# polls/urls.py
path('posts/', views.post_list_page, name='post-list'),
```

```html
{# post_list.html #}
{% for post in posts %}
  <h3>{{ post.title }}</h3>
  <div>{{ post.content|safe }}</div>
{% endfor %}
```

Створіть «шкідливі» пости через API (лише у своєму локальному проєкті):

```bash
curl -i -X POST http://127.0.0.1:5000/api/posts/ -H "Authorization: Token ВАШ_ТОКЕН" -H "Content-Type: application/json" -d '{"title": "<script>alert(1)</script>", "content": "<img src=x onerror=alert(2)>"}'
```

Відкрийте `/posts/`. Заголовок показано як звичайний текст, бо Django його екранував. А `content` виводиться з `|safe`, тому браузер виконує код і показує вікно `alert`. Це XSS: ми самі вимкнули захист.

**Виправлення.** Приберіть `|safe`:

```html
<div>{{ post.content }}</div>
```

Тепер код виводиться як текст.

**Правила захисту від XSS:**

- Не використовуйте `|safe` і `mark_safe()` для даних користувача. Якщо HTML справді дозволений (наприклад, у статті), очищайте його бібліотекою-санітайзером (наприклад, `nh3`).
- У JavaScript виводьте дані користувача через `textContent`, а не `innerHTML`.
- Захищає саме **екранування під час виводу**, а не «фільтрація на вході».
- Додатковий шар захисту — політика CSP (Content Security Policy). У новіших версіях Django є вбудована підтримка, для старіших використовують пакет `django-csp`; перевірте документацію вашої версії.
- Cookie з `HttpOnly` не дозволяє скрипту прочитати сесію, але XSS усе одно може робити запити від імені користувача.

Щодо JavaScript:

```js
message.innerHTML = 'Помилка: ' + text;    // небезпечно, якщо text містить дані користувача
message.textContent = 'Помилка: ' + text;  // безпечно
```

У шаблоні із заняття 47 ми свідомо використовували `textContent`. Зверніть увагу: `<script>` через `innerHTML` не виконується, але `<img onerror=...>` виконується.

## 6. CSRF і чим він відрізняється від XSS

Ці дві атаки часто плутають, але вони різні.

**CSRF (підроблений міжсайтовий запит).** Ви залогінені в нашому сайті. Ви відкриваєте чужий шкідливий сайт, і той змушує ваш браузер надіслати запит до нашого сайту. Браузер сам додає cookie сесії, тому сервер вважає запит справжнім. Зловмисник не бачить відповіді й не може прочитати токен, але може виконати дію від вашого імені. Захист Django: **CSRF-токен** у формі або заголовку (чужий сайт його не знає) і `SameSite`-cookie.

|  | CSRF | XSS |
| --- | --- | --- |
| Де виконується код зловмисника | на чужому сайті; наш сайт лише отримує запит | на нашому сайті, у нашій сторінці |
| Що використовує | автоматичне надсилання cookie браузером | дані, які ми вивели без екранування |
| Що може зловмисник | змусити виконати дію від імені користувача, але не бачить відповіді | майже все, що може користувач, зокрема прочитати CSRF-токен |
| Захист | CSRF-токен, `SameSite`, перевірка `Origin` | екранування виводу, без `safe`, `textContent`, CSP |

**Висновок:** XSS обходить CSRF-захист, бо скрипт працює всередині нашої сторінки й бачить токен. Тому недостатньо захиститися лише від однієї з атак.

**Перевірка.** Надішліть POST на форму реєстрації без CSRF-токена:

```bash
curl -i -X POST http://127.0.0.1:5000/register/ -d "username=newuser&password1=Str0ng-pass-123&password2=Str0ng-pass-123"
```

Очікуваний результат: 403 (перевірка CSRF не пройшла). Те саме в браузері: тимчасово приберіть `{% csrf_token %}` з `register.html`, відправте форму й побачите 403. Поверніть тег.

Декоратор `@csrf_exempt` вимикає захист для view. Не використовуйте його без дуже вагомої причини.

**Про API.** Запити з токеном у заголовку не залежать від cookie, тому для них CSRF не загрожує. А якщо API використовує сесію (як сторінка з `fetch` на занятті 47), DRF вимагає CSRF-токен, тому ми передавали заголовок `X-CSRFToken`.

## 7. Контроль доступу та надмірні поля серіалізатора

**Порушений контроль доступу.** Сервер не перевіряє, чи має користувач право на *конкретний* об'єкт. Користувач змінює `id` в адресі й отримує чужі дані. Завдяки `IsAuthorOrReadOnly` із заняття 47 Боб отримує 403 при спробі змінити пост Аліси. Правило: **права перевіряє сервер**, а приховані кнопки в інтерфейсі нічого не захищають.

**Надмірні поля (mass assignment).** Якщо серіалізатор приймає від клієнта поле, яке не мало б змінюватися, клієнт може його підробити. Тимчасово приберіть `read_only_fields = ['author']` із `BlogPostSerializer` і створіть пост від імені Боба, вказавши автора Аліси (`1` замініть на id Аліси):

```bash
curl -i -X POST http://127.0.0.1:5000/api/posts/ -H "Authorization: Token ТОКЕН_БОБА" -H "Content-Type: application/json" -d '{"title": "Підробка", "content": "Текст", "author": 1}'
```

У відповіді 201 і `author` дорівнює id Аліси: пост створено від чужого імені. Поверніть `read_only_fields`.

**Небезпека `fields = '__all__'`.** Кожне нове поле моделі автоматично стає доступним у API. Тому краще явно перелічувати поля:

```python
class BlogPostSerializer(serializers.ModelSerializer):
    class Meta:
        model = BlogPost
        fields = ['id', 'title', 'content', 'created_at', 'author']
        read_only_fields = ['id', 'created_at', 'author']
```

**Приклад із вашого проєкту.** У моделі `Task` є унікальне поле `email`. З `fields = '__all__'` будь-який користувач, який увійшов, бачить email-адреси всіх. Зробіть поле «лише для запису»: сервер його приймає, але не віддає:

```python
class TaskSerializer(serializers.ModelSerializer):
    class Meta:
        model = Task
        fields = ['id', 'status', 'description', 'priority', 'email', 'updated_at']
        read_only_fields = ['id', 'updated_at']
        extra_kwargs = {'email': {'write_only': True}}
```

Не викидайте `email` із `fields` зовсім: поле обов'язкове в моделі, і створення завдання через API завершиться помилкою бази.

Якщо дані мають бачити лише власники, фільтруйте набір записів. Це приклад-шаблон: у вашій моделі `Task` поля `owner` поки немає.

```python
def get_queryset(self):
    return Task.objects.filter(owner=self.request.user)
```

## 8. Паролі, throttling і залежності

**Паролі.** Django ніколи не зберігає пароль у відкритому вигляді. Перевірте в оболонці:

```python
from django.contrib.auth import get_user_model
User = get_user_model()
print(User.objects.get(username='alice').password)
```

У виводі буде довгий рядок із назвою алгоритму, сіллю й хешем. Навіть адміністратор не бачить пароль. Спробуйте зареєструвати користувача зі слабким паролем (`12345678` або `qwerty123`) через `/register/`: форма відхилить його завдяки `AUTH_PASSWORD_VALIDATORS` у налаштуваннях.

**Throttling (обмеження частоти запитів)** захищає від підбору паролів і перевантаження. У `settings.py` до наявних ключів `REST_FRAMEWORK` додайте нові:

```python
REST_FRAMEWORK = {
    # ...наявні ключі...
    'DEFAULT_THROTTLE_CLASSES': [
        'rest_framework.throttling.AnonRateThrottle',
        'rest_framework.throttling.UserRateThrottle',
    ],
    'DEFAULT_THROTTLE_RATES': {
        'anon': '60/min',
        'user': '300/min',
        'token': '5/min',
    },
}
```

Стандартний `obtain_auth_token` не має обмежень (його власний список throttle-класів порожній), тому глобальні налаштування на нього не діють. Саме цей маршрут найбільше цікавить зловмисника, що підбирає паролі. Додаємо власний клас:

```python
# polls/api_models.py
from rest_framework.authtoken.views import ObtainAuthToken
from rest_framework.throttling import AnonRateThrottle


class TokenRateThrottle(AnonRateThrottle):
    scope = 'token'


class ThrottledObtainAuthToken(ObtainAuthToken):
    throttle_classes = [TokenRateThrottle]
```

```python
# polls/urls.py (замість obtain_auth_token)
path('api/token/', ThrottledObtainAuthToken.as_view(), name='api-token'),
```

Надішліть сім запитів із неправильним паролем поспіль: перші п'ять повертають 400, далі 429 Too Many Requests.

Лічильник throttling зберігається в кеші. На кількох процесах сервера потрібен спільний кеш (наприклад, Redis), інакше обмеження діє окремо в кожному процесі.

**Залежності.** Уразливості знаходять і в бібліотеках, не лише в нашому коді:

```bash
pip list --outdated
pip install pip-audit
pip-audit
```

`pip-audit` перевіряє встановлені пакети за базою відомих вразливостей. Підтримуйте Django на версії, яка ще отримує оновлення безпеки, і фіксуйте версії залежностей у `requirements.txt`.

## 9. Тести безпеки

Важливий принцип: перевіряємо не лише що працює, а й що **не працює для зловмисника**. Додайте до `polls/tests.py` (до наявних імпортів додайте `Client`, `TestCase`, `cache`, `Task`):

```python
from django.core.cache import cache
from django.test import Client, TestCase

from .models import BlogPost, Task


class SecurityTests(TestCase):
    def test_title_is_escaped_in_page(self):
        BlogPost.objects.create(title='<script>alert(1)</script>', content='Текст')
        response = self.client.get('/posts/')
        self.assertNotContains(response, '<script>alert(1)</script>')
        self.assertContains(response, '&lt;script&gt;')

    def test_post_without_csrf_token_is_rejected(self):
        client = Client(enforce_csrf_checks=True)
        response = client.post('/register/', {
            'username': 'newuser',
            'password1': 'Str0ng-pass-123',
            'password2': 'Str0ng-pass-123',
        })
        self.assertEqual(response.status_code, 403)

    def test_password_is_not_stored_in_plain_text(self):
        user = User.objects.create_user('hashuser', password='pass12345')
        self.assertNotEqual(user.password, 'pass12345')
        self.assertTrue(user.check_password('pass12345'))


class ApiSecurityTests(APITestCase):
    def setUp(self):
        cache.clear()
        self.alice = User.objects.create_user('alice', password='pass12345')
        self.bob = User.objects.create_user('bob', password='pass12345')

    def test_author_cannot_be_forged(self):
        self.client.force_authenticate(user=self.bob)
        data = {'title': 'T', 'content': 'C', 'author': self.alice.pk}
        response = self.client.post('/api/posts/', data, format='json')
        self.assertEqual(response.status_code, status.HTTP_201_CREATED)
        self.assertEqual(response.data['author'], self.bob.pk)

    def test_task_email_is_not_exposed(self):
        Task.objects.create(email='secret@example.com', description='x')
        self.client.force_authenticate(user=self.bob)
        response = self.client.get('/api/tasks/')
        self.assertNotContains(response, 'secret@example.com')

    def test_token_endpoint_is_throttled(self):
        creds = {'username': 'alice', 'password': 'wrong'}
        codes = [
            self.client.post('/api/token/', creds, format='json').status_code
            for _ in range(7)
        ]
        self.assertIn(status.HTTP_429_TOO_MANY_REQUESTS, codes)
```

Тест `test_task_email_is_not_exposed` працює, якщо `TaskViewSet` зареєстровано за адресою `/api/tasks/` (домашнє завдання заняття 47). Тест на XSS потребує сторінки `/posts/` без `|safe`.

Корисна вправа: тимчасово виведіть заголовок із `|safe` (`{{ post.title|safe }}`) і запустіть тести. `test_title_is_escaped_in_page` впаде. Приберіть `|safe`, і тест знову зелений. Так видно, що тест справді охороняє захист.

Наприкінці запустіть `python manage.py check --deploy` ще раз (із змінними з розділу 3) і порівняйте кількість попереджень із початком. Для автоматичної перевірки в CI можна додати `python manage.py check --deploy --fail-level WARNING`.

## 10. Чек-ліст безпеки Django-проєкту

1. `DEBUG=False`, `SECRET_KEY` і `ALLOWED_HOSTS` у змінних оточення.
2. HTTPS, захищені cookie, HSTS.
3. ORM замість зібраного вручну SQL; параметри в `raw()`.
4. Без `|safe` і `mark_safe` для даних користувача; `textContent` у JavaScript.
5. CSRF-захист увімкнено; без `@csrf_exempt` без причини.
6. Права перевіряє сервер: дозволи DRF й об'єктні дозволи.
7. Явні `fields` у серіалізаторах; чутливі поля `read_only` або `write_only`.
8. Throttling, особливо на вході й отриманні токена.
9. Залежності оновлюються; `pip-audit` у процесі.
10. Негативні тести безпеки й `check --deploy` у CI.

## 11. Типові помилки

1. **`KeyError: 'DJANGO_SECRET_KEY'`.** Змінну не задано в цьому терміналі. Задайте її перед запуском сервера.
2. **400 на всіх запитах при `DEBUG=0`.** Хост не в `ALLOWED_HOSTS`.
3. **Зникло оформлення адмінки при `DEBUG=0`.** Це очікувано: `runserver` не віддає статику без `DEBUG`.
4. **Після `DJANGO_HTTPS=1` локальний сервер «не відкривається».** Він перенаправляє на `https://`. Не вмикайте цю змінну для локальної роботи.
5. **`alert` не спрацьовує на `/posts/`.** Перевірте, що в шаблоні є `|safe` і що в пості саме `<img onerror=...>`; `<script>` через `innerHTML` не виконується.
6. **429 у звичайних тестах.** Спрацювало обмеження частоти. Додайте `cache.clear()` у `setUp` або збільште ліміти.
7. **`assertContains` не знаходить екранований рядок.** Django екранує апостроф як `&#x27;`, тому не порівнюйте повні рядки з апострофами.
8. **`.env` не підхоплюється.** Django сам його не читає: потрібен `python-dotenv` або `django-environ`, або просто задайте змінні в терміналі.

## 12. Словничок

- **OWASP Top 10**: список найпоширеніших категорій вразливостей веб-застосунків.
- **`SECRET_KEY`**: ключ, яким Django підписує сесії та токени. Не зберігається в git.
- **`ALLOWED_HOSTS`**: список дозволених доменів сайту.
- **HTTPS**: захищене з'єднання з шифруванням.
- **HSTS**: правило, що змушує браузер відкривати сайт лише через HTTPS.
- **SQL-ін'єкція**: підміна змісту SQL-запиту через дані користувача.
- **XSS**: чужий скрипт, що виконується на нашому сайті.
- **CSRF**: чужий сайт змушує браузер надіслати запит до нашого від імені користувача.
- **CSRF-токен**: значення, що підтверджує, що форма прийшла з нашого сайту.
- **Екранування**: заміна символів `<`, `>` та інших на безпечні відповідники.
- **Mass assignment**: клієнт підробляє поле, яке не мало б змінюватися.
- **Throttling**: обмеження кількості запитів за час.
- **IDOR / порушений контроль доступу**: доступ до чужого об'єкта через зміну `id`.
- **Хеш пароля**: необоротний «відбиток» пароля, який зберігається замість самого пароля.

## 13. Запитання для самоперевірки

Спробуйте відповісти без підглядання, потім звірте з відповідями нижче.

1. Від чого Django захищає із коробки, а де відповідальність на розробнику?
2. Що робить `check --deploy`?
3. Чому не можна лишати `DEBUG=True` у продакшені?
4. Для чого потрібен `SECRET_KEY` і що робити, якщо він потрапив у git?
5. Що захищає `ALLOWED_HOSTS`?
6. Чому ORM захищає від SQL-ін'єкцій, а `raw()` з f-рядком ні?
7. Чому заголовок на сторінці безпечний, а поле, виведене з `|safe`, ні?
8. Як безпечно вивести дані користувача в JavaScript?
9. Чим CSRF відрізняється від XSS?
10. Чому XSS небезпечніший для CSRF-захисту?
11. У чому небезпека `fields = '__all__'`?
12. Що робить `write_only` для поля?
13. Чому глобальні налаштування throttling не захищають `/api/token/`?
14. Навіщо потрібні негативні тести безпеки?

**Відповіді.**

1. Із коробки Django екранує шаблони, вимагає CSRF-токен, будує безпечні запити в ORM, хешує паролі. Розробник відповідає за налаштування та за місця, де він обходить захист (`|safe`, сирий SQL, `@csrf_exempt`, `__all__`).
2. Перевіряє налаштування проєкту на типові проблеми безпеки для продакшену.
3. Помилка показує код, налаштування й значення змінних, а 404 перелічує всі маршрути.
4. Ним підписуються сесії й токени скидання пароля; якщо він потрапив у git, його вважають витеклим і генерують новий.
5. Захищає від підміни заголовка `Host`.
6. ORM передає значення окремо від тексту запиту, а в f-рядку значення стає частиною SQL.
7. Заголовок екранується автоматично, а `|safe` вимикає екранування.
8. Через `textContent`, а не `innerHTML`.
9. У CSRF запит надсилає чужий сайт, а наш лише отримує його; у XSS шкідливий код виконується на нашому сайті.
10. Скрипт на нашій сторінці бачить CSRF-токен і може ним скористатися.
11. Нові поля моделі автоматично потрапляють в API, зокрема чутливі.
12. Сервер приймає значення, але не віддає його у відповіді.
13. Стандартний `obtain_auth_token` має порожній список throttle-класів.
14. Вони перевіряють, що зловмисник справді не може виконати заборонену дію, і ловлять регресії в захисті.
