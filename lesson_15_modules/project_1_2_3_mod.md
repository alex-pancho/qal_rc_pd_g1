# Практика 15: Що робимо в проєктах після лекції «Модулі та Пакети»

## Контекст: де ми зараз

До заняття 15 проєкт існує як один або кілька файлів із класами, функціями і `main.py`. Все, можливо, працює — але код зростає, і тримати його в одному місці стає незручно. Заняття 15 — це момент, коли ми зупиняємось і **наводимо лад у структурі**, перш ніж рухатись далі до файлів, баз даних і мережі.

Головна ідея: **не переписувати логіку, а правильно розкласти те, що вже є.**

## Проєкт 1: Task & Bug Manager

### Що маємо зараз

Класи `User`, `Issue`, `TaskManager` з методами, обробкою винятків і головним меню в `main.py`. Усе, швидше за все, в одному або двох файлах.

### Що зробити

**Перетворити проєкт на пакет `task_manager`** з такою структурою:

```
task_manager/
    __init__.py
    models.py
    manager.py
    exceptions.py
    cli.py
main.py
```

**`models.py`** — сюди переїжджають усі класи-сутності:
- клас `User`
- клас `Issue` та його підкласи (`Task`, `Bug`, `TestCase` — якщо вже є)

**`exceptions.py`** — сюди виносяться власні класи винятків:
- `IssueNotFoundError`
- `InvalidMenuChoiceError`
- та інші, які вже є або мають бути

**`manager.py`** — сюди переїжджає клас `TaskManager` з усією бізнес-логікою:
- `create_issue()`
- `delete_issue()`
- `list_issues()`
- `change_status()`

**`cli.py`** — сюди виноситься логіка меню та взаємодії з користувачем:
- функція `show_menu()`
- функція `handle_choice()`
- або клас `CLI`, якщо хочеш зробити акуратніше

**`__init__.py`** — виставляє назовні лише те, що потрібно `main.py`:
```python
from task_manager import TaskManager, run
```

**`main.py`** — залишається мінімальним:
```python
from task_manager import run

if __name__ == "__main__":
    run()
```

### На що звернути увагу

- `models.py` не імпортує нічого з `manager.py` — залежність лише в один бік
- `manager.py` імпортує з `models.py` та `exceptions.py`
- `cli.py` імпортує з `manager.py` — але `manager.py` нічого не знає про `cli.py`
- У `main.py` не повинно залишитись жодної логіки

## Проєкт 2: Expense & Budget Tracker

### Що маємо зараз

Класи `Transaction`, `Income`, `Expense`, `Budget`, `ExpenseTracker` з валідацією, захищеними атрибутами і методами розрахунку балансу.

### Що зробити

**Перетворити проєкт на пакет `expense_tracker`** з такою структурою:

```
expense_tracker/
    __init__.py
    models.py
    tracker.py
    exceptions.py
    cli.py
main.py
```

**`models.py`** — усі класи-сутності:
- абстрактний `Transaction`
- підкласи `Income` та `Expense`
- клас `Budget`

**`exceptions.py`** — власні винятки:
- `InvalidAmountError`
- `TransactionNotFoundError`
- `BudgetExceededError` — якщо вже є або плануєш додати

**`tracker.py`** — клас `ExpenseTracker` з бізнес-логікою:
- `add_transaction()`
- `delete_transaction()`
- `calculate_balance()`
- `monthly_report()`

**`cli.py`** — меню та введення користувача

**`__init__.py`** — публічний інтерфейс пакету

**`main.py`** — лише точка входу

### Додатковий крок — константи

На цьому етапі зручно додати файл `constants.py` із переліком категорій витрат і доходів:

```
expense_tracker/
    __init__.py
    models.py
    tracker.py
    exceptions.py
    constants.py
    cli.py
main.py
```

У `constants.py` — просто іменовані константи або `Enum` для категорій: `"Зарплата"`, `"Їжа"`, `"Оренда"` тощо. Це підготовка до наступних модулів, де ці категорії будуть потрібні у JSON і базі даних.

### На що звернути увагу

- `models.py` не знає про `tracker.py` — клас `Income` не викликає нічого з `ExpenseTracker`
- `tracker.py` імпортує з `models.py` та `exceptions.py`
- `constants.py` імпортується звідусіль, але сам не імпортує нічого зсередини пакету

## Проєкт 3: Service Management System

### Що маємо зараз

Абстрактний базовий клас `Order` або `Appointment`, підкласи для різних типів, клас `Client`, клас `ServiceManager` з валідацією та захищеними атрибутами.

### Що зробити

**Перетворити проєкт на пакет** з такою структурою (назва залежить від обраного домену):

```
service_manager/         # або auto_service / beauty_clinic
    __init__.py
    models/
        __init__.py
        client.py
        order.py
        service.py
        inventory.py
    manager.py
    exceptions.py
    cli.py
main.py
```

Цей проєкт отримує **вкладений пакет `models`** — бо сутностей тут більше, ніж в інших проєктах, і тримати їх усіх в одному файлі вже незручно.

**`models/client.py`** — клас `Client` (або `Customer`)

**`models/order.py`** — абстрактний `Order` і всі його підкласи

**`models/service.py`** — клас `Service` або `Procedure`

**`models/inventory.py`** — клас для обліку запчастин або препаратів (якщо вже є)

**`models/__init__.py`** — збирає всі моделі в одному місці, щоб зовні писати просто:
```python
from service_manager.models import Client, RepairOrder, Service
```

**`manager.py`** — клас `ServiceManager` з бізнес-логікою

**`exceptions.py`** — власні винятки:
- `ClientNotFoundError`
- `InvalidPriceError`
- `OrderNotFoundError`

**`cli.py`** — меню та взаємодія з користувачем

### На що звернути увагу

- Вкладений пакет `models/` — це не ускладнення заради ускладнення: тут справді є чотири різні сутності, кожна зі своєю логікою
- `models/__init__.py` — це «рецепція» підпакету: імпортуєш з нього і не думаєш, в якому саме файлі лежить потрібний клас
- `manager.py` імпортує з `models/`, але жоден файл у `models/` не знає про `manager.py`

## Загальне для всіх трьох проєктів

### Що перевірити після рефакторингу

| Питання | Очікувана відповідь |
|---|---|
| `main.py` містить логіку? | Ні — лише виклик `run()` або аналогічного |
| Є циклічні імпорти? | Ні — залежності йдуть в один бік |
| `__init__.py` розкриває внутрішні деталі? | Ні — лише публічний інтерфейс |
| Програма працює так само, як до рефакторингу? | Так — поведінка не змінилась |

### Що НЕ потрібно робити на цьому етапі

- Не потрібно додавати нову функціональність — лише перекласти існуючу
- Не потрібно чіпати логіку класів — вона вже правильна після занять 10–14
- Не потрібно думати про збереження даних — це заняття 16–18

### Головний критерій успіху

Якщо після рефакторингу `main.py` виглядає як:

```python
from назва_пакету import run

if __name__ == "__main__":
    run()
```

— структура зроблена правильно.
