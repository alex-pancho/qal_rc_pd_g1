## Теоретична частина

### Навіщо потрібне віртуальне середовище

Віртуальні середовища забезпечують просте вирішення безлічі потенційних проблем. Зокрема, вони допоможуть:

- вирішити проблеми з залежностями, дозволяючи використовувати різні версії пакету для різних проєктів. Наприклад, можна використовувати пакет A v2.7 для проєкту X та пакет A v1.3 для проєкту Y;
- зробити свій проєкт самодостатнім та відтворюваним, зафіксувавши усі залежності пакетів у файлі вимог;
- встановити пакети на хост, до якого відсутні права адміністратора;
- підтримувати свій глобальний каталог site-packages/ охайним, усунувши необхідність встановлювати пакети для всієї системи, які можуть знадобитися лише для одного проєкту.

Уявіть ситуацію: ви розробляєте два проєкти на одному комп'ютері. Перший потребує бібліотеки `requests` версії `2.28`, а другий — `requests` версії `2.31`. Якщо встановлювати пакети глобально, один із проєктів обов'язково зламається.

Саме для цього існують **віртуальні середовища** — ізольовані «копії» Python зі своїм набором бібліотек, які не конфліктують із системними та між собою.

**Проблеми без ізоляції:**

- Конфлікт версій між різними проєктами.
- Засмічення системного Python зайвими пакетами.
- Відсутність можливості точно відтворити середовище на іншій машині.
- Ризик зламати системні утиліти, що залежать від стандартних версій Python.

**Переваги віртуального середовища:**

- Кожен проєкт має власний, незалежний набір пакетів.
- Просте відтворення середовища за допомогою файлу залежностей.
- Жоден проєкт не впливає на інші.
- Чистота системного Python.

### venv — стандартний інструмент Python

`venv` — це стандартний модуль Python (вбудований, без додаткового встановлення), який створює ізольоване середовище у вказаній папці.

Щоразу, коли треба працювати над проєктом Python, який використовує зовнішні залежності, які встановлені за допомогою pip (або використана інша утіліта для керування залежностями), найкраще спочатку створити віртуальне середовище.

#### Створення середовища

```bash
# Загальний синтаксис: python -m venv <назва_папки>
# Стандартна угода — назва .venv (крапка приховує папку у Unix-системах)
python -m venv .venv
```

Після виконання команди у поточній директорії з'явиться папка `.venv` зі своєю копією Python, `pip` та порожньою директорією для пакетів.

#### Активація середовища

Перед роботою середовище потрібно **активувати** — це змінює системні змінні так, щоб команди `python` та `pip` вказували на ізольовану копію, а не на системний Python.

```bash
# Windows (Command Prompt)
.venv\Scripts\activate.bat

# Windows (PowerShell)
.venv\Scripts\Activate.ps1

# macOS і Linux
source .venv/bin/activate
```
Перш ніж запустити цю команду, переконайтеся, що ви перебуваєте у директорії, яка містить щойно створене віртуальне середовище.

Після активації у термінальному рядку з'явиться префікс `(.venv)`:

```
(.venv) user@machine:~/project$
```

#### Деактивація середовища

```bash
deactivate
```

> **Важливо:** Папку `.venv` ніколи не додають до Git. Вона генерується автоматично і специфічна для кожної операційної системи. Завжди додавайте `.venv/` до `.gitignore`.

### pip — менеджер пакетів

`pip` — стандартний менеджер пакетів Python. Після активації `venv` всі команди `pip` встановлюють пакети виключно у поточне віртуальне середовище.

#### Основні команди

```bash
# Встановити пакет
pip install requests

# Встановити конкретну версію
pip install requests==2.31.0

# Встановити версію не нижче певної
pip install "requests>=2.28.0"

# Оновити пакет до останньої версії
pip install --upgrade requests

# Видалити пакет
pip uninstall requests

# Показати список встановлених пакетів
pip list

# Показати детальну інформацію про пакет
pip show requests
```

`pip` працює як менеждер пакетів за замовчуванням, його вартовикористовувати для встановлення зовнішніх пакетів Python. Оскільки спочатку створили та активували віртуальне середовище, pip пакети буде встановлено до ізольованного місця.

Тепер можна інсталювати пакети у своєму віртуальному середовищі. Щоб дійти до цього моменту, треба почати зі створення віртуального середовища Python під назвою venv, а потім активувати його під час поточного сеансу оболонки.

Якщо не закрити термінал, кожен пакет Python, який буде встановлено, опиниться у цьому ізольованому середовищі замість глобальних пакетів сайтів Python. Це означає, що тепер можна працювати над власним проєктом Python, не турбуючись про конфлікти залежностей.

#### Пошук пакетів

Усі публічні пакети доступні на **PyPI** (Python Package Index) — `https://pypi.org`. Саме звідти `pip` завантажує їх за замовчуванням.

### pip freeze та відтворення середовища

Щоб інший розробник (або ви самі на новій машині) міг відтворити точно таке ж середовище, використовують файл `requirements.txt`.

#### Фіксація залежностей

```bash
# Виводить усі встановлені пакети з точними версіями
pip freeze

# Зберігає список у файл
pip freeze > requirements.txt
```

Приклад вмісту `requirements.txt`:

```
certifi==2024.2.2
charset-normalizer==3.3.2
idna==3.6
requests==2.31.0
urllib3==2.2.1
```

#### Відтворення середовища

```bash
# На новій машині: створити venv, активувати і встановити всі залежності
python -m venv .venv
source .venv/bin/activate     # або .venv\Scripts\activate на Windows
pip install -r requirements.txt
```

> **Корисна практика:** Зберігайте `requirements.txt` у корені проєкту та додавайте його до Git. Так будь-хто зможе відтворити середовище один-в-один.


### Етапи роботи віртуального середовища:

- при створенні — __копіює структуру та необхідні файли__

Коли ви створюєте віртуальне середовище за допомогою venv, модуль відтворює структуру файлів та директорій стандартної інсталяції Python у вашій операційній системі. Python також копіює або символічно посилає до цієї структури директорій виконуваний файл Python, за допомогою якого ви викликали venv.

Ви можете знайти базову інсталяцію Python, на якій базується ваше віртуальне середовище, перейшовши за шляхом, який можна знайти під ключем home у `pyvenv.cfg`.

- __адаптує процес пошуку префіксів файлів__ — [детальніше тут](https://peps.python.org/pep-0405/#specification).

Замість того, щоб шукати os модуль для визначення розташування стандартної бібліотеки, інтерпретатор Python спочатку шукає pyvenv.cfg файл. Якщо інтерпретатор знайде цей файл та він містить home ключ, то інтерпретатор використає цей ключ, щоб встановити значення для двох змінних:

- sys.base_prefix міститиме шлях до виконуваного файлу Python, який використовувався для створення цього віртуального середовища, який можна знайти за шляхом, визначеним під home ключем у pyvenv.cfg.
- sys.prefix буде вказувати на каталог, що містить pyvenv.cfg.
Якщо інтерпретатор не знаходить pyvenv.cfg файл, він визначає, що він не працює у віртуальному середовищі й обидва, sys.base_prefix та sys.prefix потім вказуватимуть на той самий шлях.


- __посилається на вашу стандартну бібліотеку__

Виконуваний файл Python у вашому віртуальному середовищі має доступ до модулів стандартної бібліотеки інсталяції Python, на основі якої ви створили середовище. Python робить це можливим, вказуючи на шлях до файлу базового виконуваного файлу Python у home налаштуваннях у pyvenv.cfg:

![alt text](media/image.png)

Якщо ви перейдете до значення шляху виділеного рядка pyvenv.cfg та перерахуєте вміст директорії, ви знайдете базовий виконуваний файл Python, який використовували для створення віртуального середовища. Звідти ви можете перейти до директорії, яка містить стандартні бібліотечні модулі (/Lib/).

Мова Python налаштована на пошук цих модулів шляхом додавання відповідного шляху до sys.path. Під час site ініціалізації Python автоматично імпортує модуль, який встановлює значення за замовчуванням для цього аргументу.

Шляхи, до яких ваш сеанс Python має доступ, sys.path визначають, з яких місць Python може імпортувати модулі.

- це __змінює вашу змінну PYTHONPATH__

Щоб переконатися, що сценарії, які ви хочете запустити, використовують інтерпретатор Python у вашому віртуальному середовищі, venv змініть PYTHONPATH змінну середовища, до якої ви можете отримати доступ за допомогою `sys.path`.

```python
import sys
from pprint import pp
pp(sys.path)
```

У сценарії активації відбуваються дві важливі дії:

Шлях: він встановлює VIRTUAL_ENV змінну на шлях до кореневої папки вашого віртуального середовища та додає відносне розташування її виконуваного файлу Python до вашого PATH.
Командний рядок: змінює ім’я командного рядка, яке ви передали під час створення віртуального середовища. Він бере це ім’я та поміщає його в дужки, наприклад (venv).


Ці зміни забезпечують зручність віртуальних середовищ у вашій оболонці:

- Шлях: оскільки шлях до всіх виконуваних файлів у вашому віртуальному середовищі тепер знаходиться на початку вашого PATH, ваша оболонка викличе внутрішні версії pip або Python, коли ви просто вводите pip або python.
- Командний рядок: оскільки сценарій змінив ваш командний рядок, ви швидко дізнаєтеся, активоване ваше віртуальне середовище чи ні.
### uv — сучасний менеджер проєктів

`uv` — інструмент нового покоління для керування Python-проєктами, розроблений компанією Astral. Він написаний на Rust і в десятки разів швидший за `pip`.

**Що вміє `uv`:**

- Автоматично встановлювати та перемикати версії Python.
- Створювати і керувати `venv` без додаткових команд.
- Встановлювати пакети значно швидше за `pip`.
- Фіксувати залежності у `pyproject.toml` і `uv.lock`.
- Запускати скрипти у ізольованому середовищі.

#### Встановлення uv

```bash
# macOS і Linux
curl -LsSf https://astral.sh/uv/install.sh | sh

# Windows (PowerShell)
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"

# Перевірка встановлення
uv --version
```

#### Основні команди uv

```bash
# Ініціалізувати новий проєкт (створює папку з базовою структурою)
uv init my_project
cd my_project

# Ініціалізувати проєкт у поточній папці
uv init .

# Додати залежність до проєкту
uv add requests

# Видалити залежність
uv remove requests

# Запустити скрипт через uv (автоматично активує venv)
uv run main.py

# Синхронізувати середовище з uv.lock (аналог pip install -r)
uv sync
```

#### Файл pyproject.toml

`uv` використовує `pyproject.toml` — стандартний сучасний формат опису Python-проєкту:

```toml
[project]
name = "calculator"
version = "0.1.0"
description = "Arithmetic calculator"
requires-python = ">=3.12"
dependencies = [
    "requests>=2.31.0",
]
```

#### Файл uv.lock

`uv.lock` — файл з точними версіями всіх залежностей (включно з транзитивними). Його треба додавати до Git, щоб гарантувати однакове середовище для всіх розробників команди.

> **Порівняння підходів:**  
> `requirements.txt` + `pip` — класичний підхід, підтримується всіма.  
> `pyproject.toml` + `uv` — сучасний підхід, рекомендований для нових проєктів.

### Структура Python-проєкту

Добре організований проєкт має передбачувану структуру, де кожен файл і папка мають чітку відповідальність.

#### Структура після `uv init calculator`

```
calculator/
├── .venv/                  # Віртуальне середовище (не в Git)
├── .gitignore              # Список файлів, що не додаються в Git
├── pyproject.toml          # Метадані та залежності проєкту
├── uv.lock                 # Зафіксовані версії залежностей
├── README.md               # Опис проєкту
└── main.py                 # Точка входу програми
```

#### Розширена структура з пакетом

Коли проєкт зростає, логіку виносять у власний пакет:

```
calculator/
├── .venv/
├── .gitignore
├── pyproject.toml
├── uv.lock
├── README.md
├── main.py                 # Точка входу — лише запускає main()
└── calculator/             # Пакет із бізнес-логікою
    ├── __init__.py         # Ініціалізація пакету
    └── operations.py       # Функції арифметичних операцій
```

#### Файл `__init__.py`

Порожній (або з мінімальним вмістом) файл `__init__.py` перетворює звичайну папку на **пакет Python** — тобто модуль, який можна імпортувати.

```python
# calculator/__init__.py
# Може бути порожнім, або містити загальний імпорт для зручності
from calculator.operations import add, subtract, multiply, divide
```

### Точка входу main()

У Python немає жорсткого поняття «точки входу» як у C або Java, проте існує сталий патерн, який вирішує важливу проблему.

#### Проблема без `if __name__ == "__main__"`

```python
# utils.py — допоміжний модуль
def greet(name):
    return f"Привіт, {name}!"

# Цей код виконається при кожному імпорті:
print("Модуль завантажено!")  # <-- проблема
result = greet("Іван")
print(result)
```

```python
# main.py — імпортує utils
import utils  # Виведе "Модуль завантажено!" хоча ми цього не хочемо
```

#### Рішення — конструкція `if __name__ == "__main__"`

Коли Python запускає файл **напряму** (`python main.py`), він встановлює спеціальну змінну `__name__` зі значенням `"__main__"`. Коли файл **імпортується** як модуль, `__name__` містить ім'я модуля (наприклад, `"utils"`).

```python
# utils.py — правильна версія
def greet(name):
    return f"Привіт, {name}!"

# Цей блок виконається ТІЛЬКИ при запуску файлу напряму
if __name__ == "__main__":
    result = greet("Іван")
    print(result)
```
Також основну функцію можна назвати `main()`

```python
# main.py — структура точки входу
from calculator.operations import add, subtract, multiply, divide


def main():
    """Головна функція програми."""
    print("=== Калькулятор запущено ===")
    result = add(10, 5)
    print(f"10 + 5 = {result}")


if __name__ == "__main__":
    main()
```

**Переваги патерну `main()`:**

- Код можна **тестувати** — функцію `main()` можна викликати з тестів.
- Файл можна **імпортувати** як модуль без небажаних побічних ефектів.
- Чіткий **сигнал** для читача: «ось звідки починається програма».
- Дотримання **стандарту** Python-спільноти (PEP 8).
