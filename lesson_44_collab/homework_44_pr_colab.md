# Домашнє завдання

## Мета роботи

Навчитися працювати з GitHub так, як це відбувається в реальних командах розробки: створювати Pull Request, аналізувати зміни інших розробників, проводити Code Review та надавати конструктивні рекомендації щодо покращення коду.

---

## Частина 1. Реалізація власної функціональності

Продовжіть розробку власного Django-проєкту.

Реалізуйте одну нову функціональність. Це може бути:

* сторінка "Про нас";
* форма зворотного зв'язку;
* коментарі до статей;
* категорії;
* теги;
* пошук;
* пагінація;
* будь-яке інше логічне розширення вашого проєкту.

Після завершення роботи:

1. Створіть окрему гілку

```bash
git checkout -b feature/<назва_функціональності>
```

Наприклад

```bash
git checkout -b feature/comments
```

2. Зробіть кілька логічних комітів.

Приклад хороших повідомлень:

```
feat: add comment model

feat: create comment form

feat: display comments on article page

fix: validate empty comments
```

3. Відправте зміни до GitHub.

4. Створіть Pull Request.

---

# Частина 2. Проведіть Code Review

Після того як усі студенти створять Pull Request, викладач або випадковим чином, або за списком призначає кожному студенту Pull Request іншого учасника для перевірки.

Ваше завдання — провести повноцінне Code Review.

---

## Під час Review зверніть увагу на наступне

### Архітектура

* Чи логічно організований код?
* Чи відповідає він структурі Django-проєкту?
* Чи не порушує існуючу архітектуру?

---

### Читабельність

* Чи зрозумілі назви класів?
* Чи зрозумілі назви функцій?
* Чи зрозумілі назви змінних?

---

### Повторення коду

* Чи немає дублювання?
* Чи можна використати вже існуючий код?

---

### Django Best Practices

Перевірте, чи використовуються можливості Django.

Наприклад:

* `get_object_or_404()`
* `ModelForm`
* `reverse()`
* `login_required`
* ORM замість сирого SQL
* `select_related()`
* `prefetch_related()`

---

### Якість коду

Перевірте:

* стиль оформлення;
* відсутність зайвих імпортів;
* відсутність закоментованого коду;
* дотримання PEP8.

---

### Бізнес-логіка

Перевірте,

чи дійсно реалізовано поставлену задачу.

Іноді код виглядає добре,

але не вирішує проблему користувача.

---

# Частина 3. Відповідь на Code Review

Після отримання зауважень:

* ознайомтеся з усіма коментарями;
* виправте код (якщо погоджуєтесь із зауваженням);
* або аргументовано поясніть своє рішення.

У професійній команді Code Review — це діалог між розробниками, а не пошук "правих" і "винних".

---

# Що необхідно здати

Надішліть посилання на:

* репозиторій GitHub;
* Pull Request із реалізованою функціональністю;
* Pull Request (або його URL), у якому ви провели Code Review іншого студента.

# Критерії оцінювання

| Критерій                                     | Бали |
| -------------------------------------------- | ---: |
| Реалізовано нову функціональність            |   40 |
| Використано окрему Git-гілку та Pull Request |   10 |
| Код відповідає стилю проєкту                 |   10 |
| Проведено змістовне Code Review              |   25 |
| Якість та аргументованість коментарів        |   15 |

**Максимальна кількість балів — 100.**

> **Бонус (+10 балів):** якщо під час Code Review ви знайдете реальну помилку (bug), проблему продуктивності або запропонуєте суттєве покращення архітектури, а автор Pull Request погодиться із зауваженням і внесе відповідні зміни. Це максимально наближує домашнє завдання до реальної практики командної розробки.
