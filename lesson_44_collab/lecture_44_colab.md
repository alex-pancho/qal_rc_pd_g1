# DRY — Don't Repeat Yourself

Одне з головних правил програмування.

Якщо ви двічі написали однаковий код,

зупиніться.

Подумайте,

чи можна винести його в окрему функцію.

Наприклад,

погано:

```python
article.author.first_name + " " + article.author.last_name
```

десять разів.

Краще:

```python
def full_name(user):
    return f"{user.first_name} {user.last_name}"
```

і використовувати її всюди.

# KISS — Keep It Simple, Stupid

Не потрібно створювати складну архітектуру там,

де достатньо одного рядка.

Погано:

```
CommentFactoryBuilderManager
```

Добре:

```python
Comment.objects.create(...)
```

Простий код легше читати,

тестувати та підтримувати.

# Git Workflow

У професійній команді майже ніколи не працюють безпосередньо в гілці `main`.

Перед початком роботи створюється окрема гілка для нової функціональності.

Наприклад:

```bash
git checkout -b feature/comments
```

Усі зміни виконуються саме в цій гілці. Це дозволяє ізолювати нову функціональність від основної гілки проєкту, щоб інші розробники могли продовжувати працювати незалежно.

Коли робота завершена, гілка відправляється на сервер:

```bash
git push origin feature/comments
```

Після цього створюється Pull Request.

# Перед створенням Pull Request

Перед тим як просити команду перевірити ваш код, необхідно переконатися, що він актуальний.

Спочатку потрібно отримати останні зміни з основної гілки:

```bash

```

або:

```bash

```

Це дозволяє виявити конфлікти ще до створення Pull Request.

Чим раніше знайдено конфлікт, тим простіше його виправити.

# Що таке Pull Request

Pull Request — це не кнопка Merge.

Це запит до команди:

> "Будь ласка, перегляньте мій код."

Хороший Pull Request містить:

* короткий опис виконаної роботи;
* посилання на задачу в Jira;
* список змін;
* інформацію про міграції;
* інструкцію, як перевірити функціональність;
* за потреби — скріншоти інтерфейсу до та після змін.

Чим зрозуміліший опис, тим швидше колеги зможуть виконати перевірку.

# Code Review

## Code Review — одна з найважливіших практик професійної розробки

Після того як програміст завершує реалізацію нової функціональності, робота ще не закінчується. Перш ніж зміни потраплять до основної гілки проєкту (`main` або `develop`), їх перевіряють інші члени команди. Цей процес називається **Code Review**.

Code Review — це не формальність і не спосіб контролю співробітників. Його головна мета — зробити код якіснішим, знайти потенційні помилки ще до потрапляння у production, а також поширювати знання всередині команди.

У хорошій команді практично жоден рядок коду не потрапляє в основну гілку без перевірки іншим розробником.

# Навіщо потрібен Code Review

Багато Junior-розробників думають, що Code Review існує для пошуку помилок.

Насправді це лише одна з причин.

Основні цілі Code Review:

* знайти потенційні баги;
* перевірити відповідність архітектурі проєкту;
* переконатися, що новий код читається так само легко, як і старий;
* запобігти дублюванню функціональності;
* навчити менш досвідчених розробників;
* поширити знання про новий функціонал серед команди.

Якщо лише один розробник знає, як працює певний модуль, то після його відпустки або звільнення команда може зіткнутися з серйозними труднощами. Code Review допомагає уникнути таких ситуацій.

# Як читати чужий код

Початківці часто відкривають файл і починають читати його зверху вниз.

Це неефективно.

У великому проєкті файл може містити 500–1000 рядків коду.

Досвідчені розробники спочатку намагаються зрозуміти загальну картину.

Зазвичай вони рухаються за маршрутом виконання запиту.

```
Користувач
      │
      ▼
urls.py
      │
      ▼
views.py
      │
      ▼
forms.py
      │
      ▼

      │
      ▼

      │
      ▼
Database
```

Такий підхід дозволяє швидко зрозуміти:

* звідки приходять дані;
* де виконується бізнес-логіка;
* що записується в базу даних;
* який результат отримує користувач.

# Починайте з Pull Request

Ніколи не відкривайте IDE одразу.

* що саме було реалізовано;

* які файли змінилися;
* чи є міграції;
* як протестувати зміни.

Після цього вже можна відкривати код.

# Не читайте кожен рядок однаково уважно

Одна з типових помилок Junior — намагатися однаково уважно читати абсолютно весь код.

Senior працює інакше.

Спочатку він оцінює архітектуру.

Потім дивиться:

* які файли були змінені;
* чи логічно вони згруповані;
* чи не з'явилося дублювання;
* чи відповідають зміни поставленій задачі.

Лише після цього переходить до деталей.

# Перевіряйте не тільки код

Хороший Reviewer звертає увагу не лише на Python.

Він також перевіряє:

* назви файлів;
* структуру директорій;
* HTML;
* CSS;
* JavaScript;
* SQL-запити;
* міграції;
* документацію;
* README;
* тести.

Іноді найбільша проблема знаходиться не у Python-коді, а в неправильній міграції або відсутності тестів.

# На що дивитися під час Review

Під час перевірки варто поставити собі кілька запитань.

### Чи вирішує код поставлену задачу?

Найголовніше питання.

Іноді код написаний дуже красиво, але взагалі не реалізує необхідний функціонал.

### Чи немає дублювання?

Наприклад,

ви бачите однаковий метод у двох різних файлах.

Це хороший привід написати коментар.

> Ця логіка вже використовується у `ArticleService`. Чи можна її перевикористати?

### Чи відповідає код стилю проєкту?

Наприклад,

усі View написані як Class Based Views.

Новий код використовує Function Based View.

Функціонально все працює.

Але стиль проєкту порушено.

### Чи достатньо зрозумілі назви?

Погано

```python
x = Article.objects.first()

y = x.author
```

Добре

```python
article = Article.objects.first()

author = article.author
```

Назви повинні пояснювати призначення змінної.

### Чи можна зробити простіше?

Наприклад,

```python
if len(comments) > 0:
```

можна замінити

```python
if comments:
```

Менше коду — менше шансів зробити помилку.

# Як залишати коментарі

Code Review — це професійна дискусія.

Вона не повинна переходити на особистості.

Коментарі потрібно формулювати максимально нейтрально.

Добрий коментар пояснює проблему і пропонує рішення.

Наприклад:

> Тут можна використати `get_object_or_404()`, щоб уникнути ручної перевірки `None`.

> Цей метод виконує дві різні задачі. Можливо, варто розділити його на два методи.

> Мені здається, що цей запит може виконуватися повільно на великій кількості записів. Чи варто використати `select_related()`?

> Тут вже існує схожа функція в `services.py`. Можливо, краще перевикористати її.

Такі коментарі не ображають автора і пояснюють причину зауваження.

# Критикуйте код, а не людину

Порівняйте два варіанти.

Погано:

Добре:

У першому випадку оцінюють людину.

У другому — лише код.

Саме так і повинно виглядати професійне рев'ю.

# Типові помилки Junior під час Code Review

## 1. Захищати кожен рядок коду

Найпоширеніша помилка.

Junior починає доводити, що його рішення найкраще.

Насправді Review — це не суперечка.

Це спосіб знайти краще рішення.

Якщо більш досвідчений колега пропонує зміни, варто спочатку зрозуміти їхню мотивацію.

## 2. Сприймати зауваження як особисту образу

Коментар до Pull Request — це не оцінка ваших професійних якостей.

Навіть Senior-розробники регулярно отримують десятки зауважень до своїх Pull Request.

Це нормальна частина процесу розробки.

## 3. Коментувати стиль замість суті

Початківці іноді сперечаються через кількість порожніх рядків або розташування дужок, не помічаючи логічної помилки в алгоритмі.

Спочатку потрібно перевіряти:

* правильність бізнес-логіки;
* архітектуру;
* продуктивність;
* безпеку.

Стиль коду зазвичай контролюють автоматичні інструменти (`ruff`, `black`, `flake8`, `isort`).

## 4. Не запускати код перед Review

Одна з найнеприємніших ситуацій — Pull Request, який навіть не запускається.

Перед створенням PR необхідно:

* виконати всі тести;
* перевірити міграції;
* переконатися, що застосунок стартує без помилок;
* переглянути власні зміни ще раз.

## 5. Робити величезні Pull Request

Pull Request на 3000 рядків майже неможливо якісно перевірити.

Хорошою практикою вважаються невеликі зміни, які вирішують одну конкретну задачу.

Чим менший PR, тим швидше його перевірять і тим менше шансів пропустити помилку.

# Як реагувати на зауваження

Якщо Reviewer залишив коментар:

1. Прочитайте його уважно.
2. Якщо щось незрозуміло — поставте уточнювальне запитання.
3. Виправте код.
4. Позначте коментар як вирішений лише після внесення змін або досягнення домовленості.

Не варто сперечатися лише заради того, щоб "виграти" дискусію. Головна мета Code Review — зробити кодову базу якіснішою.


# Чек-лист перед відправкою Pull Request

Перед тим як натиснути кнопку **Create Pull Request**, варто перевірити:

* чи проходять усі тести;
* чи немає конфліктів з `main`;
* чи видалені тимчасові `print()` та `TODO`;
* чи не залишилося закоментованого коду;
* чи відповідають назви змінних прийнятому стилю;
* чи немає невикористаних імпортів;
* чи оновлено документацію, якщо це необхідно.

Такий підхід економить час усієї команди та демонструє професійне ставлення до роботи.
# Підсумок

Code Review — це один із найефективніших інструментів підвищення якості програмного забезпечення. Він допомагає знаходити помилки, підтримувати єдиний стиль коду, передавати знання між членами команди та навчатися на досвіді колег. Уміння грамотно читати чужий код, залишати конструктивні коментарі й спокійно сприймати зауваження є такою ж важливою професійною навичкою, як і написання коду. Саме ці навички відрізняють командного розробника від людини, яка просто вміє програмувати.

## Висновок

Написати код — лише частина роботи розробника. Значно важливіше навчитися працювати з уже існуючою кодовою базою, читати рішення інших розробників, перевикористовувати готові компоненти, дотримуватися правил командної розробки та конструктивно брати участь у Code Review. Саме ці навички дозволяють швидко адаптуватися в новій команді й ефективно працювати над великими Django-проєктами. Саме тому вони є невід'ємною частиною професійної підготовки Python/Django-розробника.
