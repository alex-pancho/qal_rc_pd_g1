## 2. Як будувати відповідь

**Структура з трьох частин:** визначення в одному реченні, потім приклад, потім коли використовувати або які обмеження.

- Погана відповідь: «Ну, це коли багато запитів до бази. Треба оптимізувати.»
- Хороша відповідь: «N+1 — це коли для списку з N об'єктів ORM робить один запит на список і ще N запитів на пов'язані об'єкти. Наприклад, у циклі `for post in BlogPost.objects.all(): print(post.author.username)` буде один запит на пости й по одному на автора. Я розв'язую це через `select_related('author')`, а для зв'язків багато-до-багатьох через `prefetch_related`. Кількість запитів перевіряю в тесті через `assertNumQueries`.»

**Тривожні сигнали у відповідях:** завчені визначення без прикладу; слова «завжди» і «ніколи»; вигадування; мовчання без пояснення ходу думок.

## 3. Банк питань: Python, Git, бази даних, HTTP

### Python

**1. Чим `list` відрізняється від `tuple`?** Список змінюваний, кортеж незмінний. Кортеж можна використати як ключ словника, якщо всі його елементи хешовані. Кортежі зручні для фіксованих наборів даних.

**2. Чим `==` відрізняється від `is`?** `==` порівнює значення, а `is` перевіряє, чи це той самий об'єкт у пам'яті. Для порівняння з `None` використовують `is None`.

**3. Чому небезпечно `def f(x, items=[])`?** Значення за замовчуванням створюється один раз при оголошенні функції, тому список спільний між усіма викликами. Правильно:

```python
def add_item(item, items=None):
    if items is None:
        items = []
    items.append(item)
    return items
```

**4. Що таке декоратор?** Функція, яка приймає функцію й повертає нову (обгортку) з додатковою поведінкою:

```python
import functools


def log_calls(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print(f'Виклик {func.__name__}')
        return func(*args, **kwargs)
    return wrapper
```

`functools.wraps` зберігає ім'я та документацію оригінальної функції. У Django ви бачили декоратори `@login_required` і `@api_view`.

**5. Що таке генератор і `yield`?** Функція з `yield` повертає ітератор, який видає значення по одному й не тримає всі дані в пам'яті. Підходить для великих або нескінченних послідовностей.

**6. Що таке `*args` і `**kwargs`?** `*args` збирає позиційні аргументи в кортеж, `**kwargs` збирає іменовані в словник. Вони дозволяють функції приймати довільну кількість аргументів.

**7. Що таке менеджер контексту (`with`)?** Конструкція, яка гарантує коректне звільнення ресурсів (закрити файл, з'єднання). Працює через методи `__enter__` і `__exit__`.

**8. Як працює `try` / `except` / `else` / `finally`?** У `try` код, що може впасти; `except` обробляє конкретний виняток; `else` виконується, якщо винятку не було; `finally` виконується завжди. Ловіть конкретні винятки, а не голий `except`.

**9. Яка складність пошуку в `list`, `set` і `dict`?** Перевірка `x in list` — O(n), а `x in set` і доступ до ключа `dict` — у середньому O(1).

**10. Чим поверхнева копія відрізняється від глибокої?** Поверхнева (`copy.copy`) копіює контейнер, але вкладені об'єкти лишаються спільними. Глибока (`copy.deepcopy`) копіює рекурсивно.

**11. Чим list comprehension відрізняється від generator expression?** `[x for x in data]` одразу будує список, `(x for x in data)` створює ліниву послідовність, яка видає значення за потребою.

**12. Чим `__str__` відрізняється від `__repr__`?** `__str__` — читабельне представлення для користувача, `__repr__` — однозначне представлення для розробника. У моделях Django `__str__` визначає, як об'єкт показується в адмінці.

**13. Що таке GIL?** У стандартному CPython лише один потік одночасно виконує байткод Python, тому потоки не прискорюють обчислення, що навантажують процесор. Для I/O (мережа, диск) потоки й async працюють добре, для CPU використовують `multiprocessing`. Існують експериментальні збірки без GIL, але це окрема тема.

**14. Навіщо віртуальне середовище?** Воно ізолює залежності проєкту від інших проєктів і від системного Python. Залежності фіксують у `requirements.txt`.

### Git

**15. Чим merge відрізняється від rebase?** Merge зберігає історію гілок і додає коміт злиття. Rebase переписує коміти поверх іншої гілки й дає лінійну історію. Спільні гілки перебазовувати не варто.

**16. Як вирішувати конфлікт?** Git позначає конфліктні місця маркерами `<<<<<<<`, `=======`, `>>>>>>>`. Ви редагуєте файл, лишаючи правильний варіант, виконуєте `git add` і завершуєте злиття чи rebase.

**17. Чим `git reset` відрізняється від `git revert`?** `reset` пересуває гілку назад і переписує історію (небезпечно для спільних гілок). `revert` створює новий коміт, що скасовує зміни, тому безпечний для спільної історії.

**18. Що таке Pull Request і навіщо він?** Запит на злиття гілки, у якому команда робить review коду, обговорює зміни й запускає автоматичні перевірки (CI).

**19. Що робити, якщо секрет потрапив у git?** Вважати його витеклим і негайно замінити (змінити пароль чи ключ). Видалення з історії — додатковий захід, але само по собі не рятує.

**20. Чим `git fetch` відрізняється від `git pull`?** `fetch` лише завантажує зміни, `pull` — це `fetch` плюс злиття (або rebase) у поточну гілку.

### Бази даних і SQL

**21. Що таке первинний і зовнішній ключ?** Первинний ключ однозначно ідентифікує рядок таблиці. Зовнішній ключ посилається на первинний ключ іншої таблиці й задає зв'язок.

**22. Чим `INNER JOIN` відрізняється від `LEFT JOIN`?** `INNER JOIN` повертає лише рядки, що мають відповідник в обох таблицях. `LEFT JOIN` повертає всі рядки лівої таблиці, а для відсутніх відповідників правої ставить `NULL`.

**23. Що таке індекс?** Структура, що прискорює пошук і з'єднання за полем. Платимо за це повільнішим записом і додатковим місцем, тому індексують поля, за якими часто шукають.

**24. Що таке транзакція й ACID?** Транзакція — група операцій, які виконуються як одне ціле. ACID: атомарність, узгодженість, ізоляція, довговічність.

**25. Чим `WHERE` відрізняється від `HAVING`?** `WHERE` фільтрує рядки до групування, `HAVING` фільтрує групи після `GROUP BY`.

### HTTP і REST

**26. Які HTTP-методи ви знаєте й що вони означають?** GET читає, POST створює, PUT замінює ресурс повністю, PATCH змінює частково, DELETE видаляє. GET, PUT і DELETE ідемпотентні, POST ні.

**27. Які коди відповіді ви використовуєте?** 200 (успіх), 201 (створено), 204 (успіх без тіла), 400 (невалідні дані), 401 (не автентифікований), 403 (немає прав), 404 (не знайдено), 405 (метод не дозволений), 429 (забагато запитів), 500 (помилка сервера).

**28. Чим 401 відрізняється від 403?** 401 — сервер не знає, хто ви. 403 — знає, але дію заборонено.

**29. Чим PUT відрізняється від PATCH?** PUT замінює ресурс повністю й вимагає всіх обов'язкових полів, PATCH змінює лише надіслані поля.

**30. Що таке REST?** Стиль API, де кожен ресурс має власну адресу, дії задаються HTTP-методами, а сервер не зберігає стан клієнта між запитами (stateless).

## 4. Банк питань: Django, REST, безпека, тестування, production

### Django

**31. Що таке MVT у Django?** Model, View, Template. Model описує дані, View обробляє запит і готує відповідь (за роллю схожий на контролер), Template відповідає за відображення.

**32. Як Django обробляє запит?** Запит проходить через middleware, URL-маршрутизація знаходить view, view працює з ORM і базою, потім формується відповідь (шаблон або JSON), яка знову проходить через middleware.

**33. Що таке QuerySet і чому він «лінивий»?** Це об'єкт запиту до бази. SQL виконується лише тоді, коли дані справді потрібні (ітерація, `list()`, `len()`), тому можна будувати запит ланцюжком `filter().order_by()` без зайвих звернень до бази.

**34. Чим `get` відрізняється від `filter`?** `get` повертає один об'єкт і кидає `DoesNotExist` (або `MultipleObjectsReturned`), `filter` повертає QuerySet. У view зручно використовувати `get_object_or_404`, щоб замість помилки 500 віддати 404.

**35. Що таке проблема N+1 і як її розв'язати?** Для списку з N об'єктів ORM робить один запит на сам список і ще N на пов'язані об'єкти. Розв'язання: `select_related` (ForeignKey, OneToOne, через JOIN) і `prefetch_related` (багато-до-багатьох і зворотні зв'язки, окремий запит).

**36. Що таке міграції?** Файли з описом змін структури бази. `makemigrations` створює їх зі змін моделей, `migrate` застосовує до бази. Міграції зберігаються в git разом із кодом.

**37. Які зв'язки є в Django і що таке `on_delete`?** `ForeignKey` (багато-до-одного), `OneToOneField`, `ManyToManyField`. `on_delete` визначає, що робити при видаленні пов'язаного об'єкта: `CASCADE` (видалити залежні), `SET_NULL` (потрібне `null=True`), `PROTECT` (заборонити видалення).

**38. Що таке middleware?** Шар, який обробляє запит перед view й відповідь після. Приклади: сесії, автентифікація, CSRF, безпека.

**39. Чим `Form` відрізняється від `ModelForm`?** `ModelForm` будується на основі моделі, перевіряє дані за її полями й вміє зберігати об'єкт. `Form` описує поля вручну.

**40. Навіщо CSRF-токен?** Він підтверджує, що форму надіслано з нашого сайту, а не підроблено на чужому. Чужий сайт не знає значення токена, тому не може підробити запит від імені користувача.

**41. Як Django зберігає паролі й сесії?** Пароль — у вигляді хешу із сіллю (за замовчуванням PBKDF2), перевірка через `check_password`. Сесія: у cookie лише ідентифікатор, а дані сесії зберігаються на сервері (за замовчуванням у базі).

**42. Як обмежити доступ до view?** Для сторінок — декоратор `login_required` чи перевірка прав користувача; для API — класи дозволів DRF. Перевірку завжди виконує сервер.

### DRF (REST API)

**43. Що таке серіалізатор?** Об'єкт, який перетворює об'єкти Python у JSON і назад та перевіряє вхідні дані. `ModelSerializer` будує поля з моделі й реалізує `create` та `update`.

**44. Чим `APIView` відрізняється від `ViewSet`, і що таке Router?** `APIView` описує окремі методи (`get`, `post`). `ViewSet` об'єднує дії (`list`, `create`, `retrieve`, `update`, `destroy`), а Router сам створює для нього адреси.

**45. Чим автентифікація відрізняється від дозволів у DRF?** Автентифікація визначає, хто робить запит (токен, сесія). Дозволи вирішують, чи можна цьому користувачу виконати дію (`IsAuthenticated`, `IsAuthenticatedOrReadOnly`, власні об'єктні дозволи через `has_object_permission`).

**46. Що таке throttling?** Обмеження кількості запитів за час (наприклад, `60/min`). При перевищенні повертається 429. Особливо важливо на вході й отриманні токена.

### Тестування

**47. Чим `TestCase` відрізняється від `APITestCase`?** Обидва виконують кожен тест на окремій тестовій базі в транзакції. `APITestCase` додає зручний клієнт для API (`self.client`) і методи на кшталт `force_authenticate`.

**48. Чим `force_authenticate` відрізняється від `credentials`?** `force_authenticate` обходить автентифікацію й одразу «вмикає» користувача (зручно для перевірки дозволів). `credentials` додає справжній заголовок (наприклад, `Token ...`) і проходить повну перевірку.

**49. Навіщо негативні тести?** Вони перевіряють, що зловмисник не може виконати заборонену дію (401, 403, 400, 404). Тест, який жодного разу не падав, не доводить нічого.

**50. Як перевірити кількість SQL-запитів?** Через `assertNumQueries` у тесті Django або django-debug-toolbar під час розробки.

### Безпека

**51. Як захиститися від SQL-ін'єкцій?** Використовувати ORM або параметризовані запити (`raw(sql, [params])`), ніколи не збирати SQL з f-рядків.

**52. Чим XSS відрізняється від CSRF?** У XSS чужий скрипт виконується на нашому сайті (захист: екранування виводу, не використовувати `|safe` для даних користувача, `textContent` у JavaScript). У CSRF чужий сайт змушує браузер надіслати запит до нашого від імені користувача (захист: CSRF-токен, `SameSite`).

**53. Що таке mass assignment і чому небезпечно `fields = '__all__'`?** Клієнт може підробити поле, яке не мало б змінюватися (наприклад, `author`). Нові поля моделі автоматично потрапляють в API. Краще явно перелічувати поля й позначати чутливі `read_only` чи `write_only`.

**54. Які налаштування Django критичні для production?** `DEBUG=False`, секретний `SECRET_KEY` у змінних оточення, правильні `ALLOWED_HOSTS`, HTTPS і захищені cookie. Перевірити можна командою `check --deploy`.

### Production

**55. Чому в production не використовують `runserver` і SQLite?** `runserver` призначений лише для розробки. SQLite — це файл, який погано витримує одночасні записи й зникає разом із контейнером. Потрібні WSGI-сервер (gunicorn) і окрема база (PostgreSQL).

**56. Як віддається статика в production?** `collectstatic` збирає її в одну папку, а віддає WhiteNoise або nginx.

**57. Що таке Docker-образ і контейнер?** Образ — шаблон із застосунком і залежностями, контейнер — його запущена копія. `docker compose` запускає кілька сервісів разом (застосунок і база).

**58. Чому міграції запускають окремим кроком?** При кількох копіях застосунку вони виконувалися б одночасно. Тому міграції — окремий крок розгортання.

**59. Які теми варто хоча б знати за назвою (поза програмою курсу)?** Сигнали Django (`signals`), кешування (Redis), черги завдань (Celery), асинхронні view. Чесно скажіть, що знайомі лише на рівні понять, і поясніть, навіщо вони потрібні.

## 5. Нетипові питання, live coding і code review

### Нетипові питання

Вони перевіряють не завчені факти, а мислення.

**Що відбувається, коли ви вводите URL у браузері й натискаєте Enter?**

1. Браузер розв'язує домен через DNS.
2. Відкриває TCP-з'єднання, а для HTTPS домовляється про TLS.
3. Надсилає HTTP-запит.
4. Запит доходить до зворотного проксі (nginx або Caddy), який передає його WSGI-серверу (gunicorn).
5. Django проганяє запит через middleware, URL-маршрутизація знаходить view.
6. View перевіряє автентифікацію й дозволи, працює з ORM і базою даних.
7. Формується відповідь (шаблон або JSON від серіалізатора) і повертається назад через middleware.
8. Браузер отримує відповідь, підтягує статику й малює сторінку.

**Сторінка працює повільно. Що ви зробите?** Спочатку виміряйте, потім виправляйте:

1. Виміряти: логи, час відповіді, кількість SQL-запитів (django-debug-toolbar).
2. Знайти вузьке місце: N+1, відсутні індекси, важкі обчислення, зовнішні виклики, велика статика.
3. Виправити: `select_related`, індекси, пагінація, кеш.
4. Перевірити знову й додати тест або моніторинг.

**Спроєктуйте API скорочувача посилань.** Йдіть за планом: вимоги, сутності, адреси, помилки, безпека. Наприклад:

| Дія | Метод і адреса | Код |
| --- | --- | --- |
| Створити коротке посилання | `POST /api/links/` | 201 (400 для некоректного URL) |
| Перейти за коротким кодом | `GET /{code}` | 302 (404, якщо коду немає) |
| Мої посилання | `GET /api/links/` | 200 |
| Видалити своє посилання | `DELETE /api/links/{id}/` | 204 (403 для чужого) |

Поле сутності `Link`: оригінальний URL, унікальний короткий код, власник, дата створення, лічильник переходів. Питання, які варто поставити інтерв'юеру: чи потрібна автентифікація, чи можна обирати власний код, скільки запитів очікується, чи потрібна статистика, чи потрібен термін дії посилань.

**Інші нетипові питання й підхід:**

- «Розкажіть про баг, який довго шукали»: відповідь за STAR; покажіть процес пошуку й що зробили, щоб не повторилося.
- «Що вам не подобається в Python або Django?»: назвіть реальний недолік і те, як із ним працюєте. Фанатизм і критика всього однаково погані.
- «Чому ми маємо взяти вас?»: швидкість навчання, конкретні проєкти, мотивація, чесність щодо рівня.
- «Ви не згодні з колегою на code review»: аргументи й дані, домовленість, ескалація лише як останній крок.
- Головоломки на оцінку (скільки..., приблизно): уточніть умови, зробіть припущення, порахуйте, перевірте на здоровий глузд.

### Live coding

**Правила:**

1. Спочатку уточніть умову й крайні випадки (порожній ввід, дублікати, від'ємні числа).
2. Проговоріть підхід, перш ніж писати код.
3. Спершу просте рішення, потім оптимізація.
4. Назвіть складність за часом і пам'яттю.
5. Перевірте код на двох-трьох прикладах уголос.
6. Якщо застрягли, скажіть про це й запропонуйте підказку собі самі.

**Три типові задачі** (потрібен Python 3.10 або новіший):

```python
from collections import Counter


def is_palindrome(text: str) -> bool:
    cleaned = [ch.lower() for ch in text if ch.isalnum()]
    return cleaned == cleaned[::-1]


def two_sum(nums: list[int], target: int) -> tuple[int, int] | None:
    seen: dict[int, int] = {}
    for index, number in enumerate(nums):
        needed = target - number
        if needed in seen:
            return seen[needed], index
        seen[number] = index
    return None


def top_words(text: str, n: int = 3) -> list[tuple[str, int]]:
    words = [word.strip('.,!?;:').lower() for word in text.split()]
    return Counter(word for word in words if word).most_common(n)
```

Складність: `is_palindrome` і `top_words` лінійні за довжиною тексту, `two_sum` працює за O(n) часу й O(n) пам'яті (наївний розв'язок із двома циклами — за O(n²)). Інтерв'юер може спитати про порожній рядок, дублікати в `two_sum` (наприклад, `[3, 3]` і ціль 6), регістр і розділові знаки.

### Code review

Знайдіть проблеми в цьому коді:

```python
def search(request):
    q = request.GET.get('q', '')
    posts = BlogPost.objects.raw(
        f"SELECT * FROM polls_blogpost WHERE title LIKE '%{q}%'"
    )
    html = ''
    for post in posts:
        html += f'<h3>{post.title}</h3><p>{post.content}</p>'
    return HttpResponse(html)


@csrf_exempt
def delete_post(request, post_id):
    BlogPost.objects.get(id=post_id).delete()
    return HttpResponse('ok')
```

**Проблеми й виправлення:**

1. SQL-ін'єкція: f-рядок у `raw()`. Виправлення: ORM `filter(title__icontains=q)` або параметри.
2. XSS: HTML збирається вручну без екранування. Виправлення: шаблон з автоекрануванням.
3. `@csrf_exempt` на view, що змінює дані.
4. Немає автентифікації й перевірки прав: будь-хто видаляє будь-який пост (порушений контроль доступу).
5. Видалення доступне будь-яким HTTP-методом, зокрема GET. Виправлення: обмежити методи або зробити DELETE через DRF.
6. `get` кидає `DoesNotExist` і дає 500 замість 404. Виправлення: `get_object_or_404`.
7. Немає пагінації й обмеження пошуку, повертається весь текст постів.
8. Немає тестів.

Виправлений пошук:

```python
def search(request):
    q = request.GET.get('q', '')
    posts = BlogPost.objects.filter(title__icontains=q)[:20]
    return render(request, 'post_list.html', {'posts': posts})
```

А видалення краще віддати в `ModelViewSet` із дозволами `IsAuthenticatedOrReadOnly` та `IsAuthorOrReadOnly`, як на занятті 47. Майже кожен пункт переліку — це тема одного із занять курсу.

## 6. Тестове завдання: навіщо й як

**Навіщо компанії дають тестове.** Щоб побачити реальний код, а не розповіді: стиль, структуру, тести, документацію. І щоб мати основу для розмови на наступному етапі.

**Навіщо воно вам.** Це практика й матеріал для портфоліо, нагода показати сильні сторони, а також спосіб оцінити компанію за якістю завдання й зворотного зв'язку.

**Застереження.** Якщо завдання схоже на реальну задачу для продукту компанії, потребує кількох днів роботи або компанія не дає жодного відгуку, це привід поставити запитання чи відмовитись.

### Процес (дев'ять кроків)

1. Двічі прочитайте вимоги й випишіть явні та неявні.
2. Уточніть незрозуміле одним листом. Якщо відповіді немає, запишіть припущення в README.
3. Заплануйте час і поставте собі дедлайн раніше за справжній.
4. Спочатку мінімальна робоча версія основних вимог, потім тести, потім оздоблення.
5. Робіть малі осмислені коміти: історія git теж частина оцінки.
6. README: що це, як запустити, як тестувати, прийняті рішення й компроміси, що зробили б далі.
7. Запуск однією командою (наприклад, `docker compose up`), файл `.env.example`, жодних секретів у git.
8. Тести на головні сценарії, зокрема негативні.
9. Перед відправкою клонуйте репозиторій у чисту папку й запустіть за власним README.

### Що перевіряють рецензенти

| Критерій | Як його задовольнити |
| --- | --- |
| Працює за інструкцією | чистий запуск за README |
| Відповідає вимогам | список вимог із позначками виконання |
| Структура й читабельність | логічні модулі, зрозумілі назви, без дублювання |
| Тести | головні й негативні сценарії |
| Безпека | без секретів у git, перевірка прав, валідація |
| Git-історія | малі осмислені коміти |
| Комунікація | README, вчасні відповіді на листи |

### Типові помилки

- немає README або він не відповідає дійсності;
- секрети в репозиторії;
- немає тестів;
- надмірне ускладнення (мікросервіси для простого CRUD);
- ігнорування частини вимог;
- код із ШІ без розуміння;
- здача після дедлайну без пояснення;
- нерозуміння власного коду на розборі.

### Про ШІ

Прочитайте правила компанії. Якщо ШІ дозволено, використовуйте його як помічника й перевіряйте результат. Якщо заборонено, не використовуйте. У будь-якому разі ви маєте пояснити кожен рядок власного рішення: це перевіряють на розборі.

### Якщо не встигаєте

Здайте робоче й чесно опишіть у README, чого бракує й чому. Це краще, ніж зламана повна версія або тиша.

### Шаблон README

```markdown
# Назва проєкту

Коротко: що робить застосунок (1–2 речення).

## Як запустити
1. Скопіюйте `.env.example` у `.env` і заповніть значення.
2. `docker compose up --build`
3. `docker compose run --rm web python manage.py migrate`

## Як перевірити

## Рішення та компроміси

```

### Перевірка перед відправкою

- Репозиторій клоновано в чисту папку й запущено за README.
- Тести проходять.
- У git немає `.env`, паролів і ключів.
- Усі вимоги закрито або описано в README, що не зроблено.
- Коміти зрозумілі, у листі-відповіді є посилання на репозиторій і короткий опис.

## 7. «Які у вас питання?»

Це питання наприкінці розмови — не формальність. Відповідь «ні, все зрозуміло» — втрачена можливість: питання показують інтерес і дозволяють вам оцінити компанію. Підготуйте п'ять питань, поставте два-три.

### Категорії питань

| Тема | Приклад питання | English |
| --- | --- | --- |
| Роль і завдання | Як виглядає типовий робочий тиждень на цій позиції? | What would a typical week look like in this role? |
| Команда | Скільки людей у команді й які ролі? Як ухвалюєте технічні рішення? | How does the team make technical decisions? |
| Процес розробки | Чи є code review, CI/CD, автотести? Як часто ви деплоїте? | How do you handle code review and testing? |
| Навчання й онбординг | Як проходить онбординг? Чи буде ментор? | What does onboarding look like? Will I have a mentor? |
| Очікування | Що для вас означає успішний перший квартал або випробувальний термін? | What would success look like in the first three months? |
| Продукт і технології | Над чим команда працює зараз? Які найбільші технічні виклики? | What are the biggest technical challenges right now? |
| Наступні кроки | Які наступні кроки в процесі й коли очікувати відповідь? | What are the next steps and timeline? |
| Закриваюче | Чи є щось у моєму досвіді, що викликає у вас сумніви? Я б хотів(ла) відповісти на це зараз. | Is there anything about my background that gives you pause? |

Закриваюче питання особливо корисне: воно дає шанс розвіяти сумніви інтерв'юера ще до кінця розмови.

### Кому яке питання

| Інтерв'юер | Про що питати |
| --- | --- |
| Рекрутер | процес, етапи, терміни, формат роботи, склад команди |
| Технічний інтерв'юер | технології, процес розробки, виклики, code review, тестування |
| Менеджер | очікування, ріст, цінності, як оцінюють результат |

### Чого не питати

- те, що легко знайти на сайті компанії («а чим ви займаєтесь?»);
- питання, які звучать як претензія;
- лише про відпустки й пільги як про перше й єдине;
- про зарплату на технічній співбесіді: це обговорюють із рекрутером на відповідному етапі.

### На що звернути увагу у відповідях

Це привід подумати, а не вирок: один пункт ще не робить компанію поганою.

- немає code review й тестів, і це подають як норму;
- «ми як сім'я» без жодних деталей про процес;
- постійні переробки й «аврали» як спосіб роботи;
- неясна відповідь про онбординг і менторство для джуніора;
- очікують від молодшого розробника роботи старшого без підтримки;
- уникають конкретики про процес.

### Вправа

Уявіть компанію: «ТОВ ШопЛайн, Django-стартап, 8 розробників, один тестувальник, деплой раз на тиждень». Запишіть три питання до технічного лідера: одне про процес, одне про онбординг і одне закриваюче.

## 8. Чек-лист підготовки до співбесіди

**До співбесіди:**

1. Прочитайте вакансію й виділіть вимоги, які ви закриваєте, і які ні (будьте чесні щодо других).
2. Дізнайтеся про компанію: продукт, технології, новини.
3. Підготуйте розповідь про себе (60–90 секунд) і вголос відрепетируйте її.
4. Підготуйте три історії за STAR (складний баг, помилка, співпраця).
5. Прогляньте банк питань і позначте ті, де відповідь не вкладається в 60 секунд.
6. Підготуйте п'ять питань до інтерв'юера.
7. Перевірте техніку: камеру, мікрофон, інтернет, редактор коду, чисту папку з проєктом.

**Під час співбесіди:**

1. Уточнюйте умову, якщо питання нечітке.
2. Думайте вголос: інтерв'юер оцінює хід думок, а не лише відповідь.
3. Не знаєте відповіді: чесно, суміжне, гіпотеза, як перевірили б.
4. Не вигадуйте досвід, якого немає: це легко перевірити наступним питанням.
5. Наприкінці ставте питання й дізнайтеся про наступні кроки.

**Після співбесіди:**

1. Запишіть питання, які поставили, і ті, на які не знали відповіді.
2. Розберіть ці питання протягом дня.
3. Напишіть короткий лист із подякою й (за потреби) відповіддю на те, що не встигли пояснити.
4. Після відмови попросіть зворотний зв'язок: навіть коротка відповідь допомагає.

Не забувайте про баланс: один невдалий раз — це дані для навчання, а не підсумок.

- Валідація: заголовок не порожній, дата виконання не в минулому при створенні.
- Тести: щонайменше десять, зокрема негативні (401, 403, 400, 404).
- README за шаблоном, файл `.env.example`, запуск однією командою.
- Опційно: CI із тестами, Swagger, throttling.

### Інше домашнє

1. Підготуйте розповідь про себе (60–90 секунд) і три історії за форматом STAR.
2. Підготуйте п'ять питань до роботодавця.
3. Оновіть README курсового проєкту за шаблоном і профіль на GitHub.
4. Пройдіть мок-співбесіду з однокурсником і запишіть три питання, на які не знали відповіді.

### Що далі

1. **Портфоліо.** Один-два проєкти на GitHub із README, тестами, Docker, CI і (за можливості) розгорнутою демо-версією.
2. **Резюме.** Одна сторінка, проєкти з посиланнями, технології без перебільшень.
3. **Практика.** Регулярно розв'язуйте невеликі задачі й проходьте мок-співбесіди одне з одним.
4. **Журнал співбесід.** Після кожної записуйте питання, на які не знали відповіді, і розбирайте їх.
5. **Вимоги вакансій.** Ринок і вимоги змінюються, тому орієнтуйтеся на актуальні вакансії та питайте в рекрутерів, як виглядає процес.
